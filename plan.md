# Go multi-tenant mBaaS

## Product and scope

Build a multi-tenant mobile backend as a service (mBaaS) for the owner's apps, websites, and games. Each project is a tenant and the boundary for users, data, files, functions, live sessions, analytics, and quotas. Deliver every product feature as an enableable plugin. Use separate project IDs for development and production. Target the existing 4 vCPU, 8 GB RAM VPS for the first production deployment when the owner is ready, and keep the Compose profile portable to managed infrastructure.

The first release includes end-user sign-in, an API for selected PostgreSQL tables, file storage, realtime subscriptions, server-side scripts, and multiplayer with private rooms and automatic matchmaking. Ship clients for browser JavaScript, Flutter, and native Android. Keep the backend protocol suitable for Zarvan Engine, whose SDK will be developed later in Zarvan's own repository. Websites can use the service from their existing host.

Use the browser admin panel for routine project operations. Create a project, install and grant permissions to its feature plugins, configure auth and workflows, manage PostgreSQL tables, write and publish Go functions, and inspect or control live sessions in the UI. Connect clients with the API URL and project ID. Use the operator CLI to bootstrap the dashboard and recover access. Deploy to the VPS with the manual Compose release script.

## Architecture and deployment

- Run one Go host for the plugin registry, project isolation, request dispatch, and permission broker. Run bundled Go plugins in supervised worker processes and separately deployed plugins over a private service protocol. Compile dashboard-authored Go in an isolated build worker and execute its WebAssembly artifacts in the isolated runner. Use PostgreSQL for durable state and queues, and a private S3-compatible object store for file bytes.
- For self-hosting, run Docker Compose on a Linux server with a TLS reverse proxy, the Go host, script compiler and runner, PostgreSQL, and a configured S3-compatible endpoint. The storage endpoint can run locally or be supplied by the operator. Expose HTTPS publicly and keep internal services private.
- For managed hosting, run the same Compose-managed Go services on a managed Linux VM behind a WebSocket-capable ingress, with managed PostgreSQL and a private object bucket. Choose a host that supports the isolation controls. Run one always-on application replica per deployment and verify ingress timeouts, storage compatibility, and sandbox enforcement in both hosting profiles.
- Version the HTTP API and socket protocol. Define requests and responses in OpenAPI and document socket message schemas alongside it. Use HTTPS/JSON for CRUD, sign-in, file metadata, and function calls. Stream file bytes and use WebSockets for subscriptions and gameplay. Standardize error codes and request IDs, and document conflict, throttling, and retry behavior.
- Use separate migration credentials for platform and project schemas. Run platform migrations before the corresponding service release and keep changes compatible with a rollback where possible. On deploy, pause new match assignments, allow a bounded room drain window, explicitly close remaining sockets, and have clients reconnect. Go's HTTP shutdown requires separate handling of upgraded connections. [Go HTTP server shutdown](https://pkg.go.dev/net/http#Server.Shutdown)

### GitHub Actions and server deployment

1. **Build and publish.** Every merge to protected `main` runs backend, compiler, runner, and contract tests in GitHub Actions. After tests pass, build the backend, compiler, and runner images for `linux/amd64` and `linux/arm64`, then publish them to public GitHub Container Registry. Use the full merge commit SHA as the release version. Publish a GitHub release manifest with that SHA and the multi-platform image digests after the complete set is available. Give publishing permissions only to the release job and keep application secrets out of image builds. [GitHub Actions image publishing](https://docs.github.com/en/actions/tutorials/publish-packages/publish-docker-images) [Multi-platform builds](https://docs.docker.com/build/ci/github-actions/multi-platform/)
2. **Pull and migrate.** The operator manually runs the deployment script on the production server with the desired release SHA. The script acquires a deployment lock, fetches the matching manifest from the configured GitHub repository, validates the release and Compose config, and pulls the pinned images from public GHCR before interrupting the service. Keep Compose configuration, environment secrets, and persistent volumes on the server. After the drain window, stop the old application replica and run the release's one-shot migration through Compose when required. [GitHub Container Registry](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry) [Docker Compose pull](https://docs.docker.com/reference/cli/docker/compose/pull/)
3. **Start and verify.** Start the selected images with Docker Compose using `--no-build`. Check API readiness, PostgreSQL access, and the health of enabled workers before recording the version as deployed. Keep the last healthy image set for rollback. On failure, restore that set when the database schema is compatible. For incompatible migrations, use the release's documented recovery procedure and a verified backup. Expect a brief interruption during rollout. [Docker Compose up](https://docs.docker.com/reference/cli/docker/compose/up/)

Use a local Compose test stack with dedicated credentials and test data. Run release smoke checks locally before manually promoting a version to the VPS. Use the VPS location as the initial game region and check latency from the intended player networks before launch.

## Plugins and lifecycle

Register all feature surfaces through the same plugin system, including admin UI, workflows, sign-in, table and file APIs, subscriptions, scripts, rooms, invites, matchmaking, game runtimes, and Eye analytics. The Go host supplies shared configuration, isolation, authentication and policy enforcement, transport, limits, and dispatch. The operator CLI can repair configuration even with every feature plugin disabled.

### Author and install

- A plugin declares a stable ID, immutable version, host API compatibility, dependencies, requested capabilities, extension points, and a configuration schema. Register plugins written by the team or reviewed by the operator. Pin the reviewed artifact or service version. Provide common manifest, config validation, and readiness hooks. Authors implement only the feature hooks they use, such as an admin page, a workflow action, an API route, a job, an event consumer, a matchmaking policy, or a room runtime. The host owns activation, revocation, and cleanup of registered work. Ship a small plugin SDK, a minimal example in each installation mode, and a contract test harness. Use the manifest schema to render settings in the dashboard.
- **In the Go build.** Bundle versioned Go worker executables and their manifests in the release image through GitHub Actions. The host starts workers on demand under an isolated identity with restricted filesystem, network, process, CPU, and memory access. Use the same plugin protocol over private local IPC. Keep active room workers attached for the life of their rooms and reclaim idle capacity. Project installation and activation happen at runtime. [Go plugin deployment considerations](https://pkg.go.dev/plugin#hdr-Warnings)
- **As an external service.** Deploy a plugin separately and register its approved private endpoint with the operator CLI or dashboard. Negotiate its manifest and host API version over the versioned HTTPS/JSON protocol. Give each project installation a dedicated worker and service identity with scoped host access. Register or upgrade the service independently of the backend image.
- **Shared permission broker.** Both Go paths receive the same scoped inputs and use typed host calls or validated write intents for platform effects. Check the intersection of the actor's permissions or trigger identity, the current project installation grants, and the effective matchmaking grants. Bound request duration, concurrency, and payloads. Keep database credentials and operator tokens in the host. Use short-lived invocation credentials scoped to the plugin, project, operation, and configuration. Recheck grants and lifecycle at commit.
- Dashboard-authored Go bundles compile to WebAssembly and use the function sandbox. Register their published entry points through the functions and turn-rules plugins, with the same version and scope checks as other features.

### Install and grant permissions per project

Server registration makes a version available. A project operator installs it for one project and grants the specific capabilities and resources it can use. Example grants include reading a named table, replacing a project admin page, or registering a workflow action. The dashboard shows requested capabilities, required and optional grants, and the exact resources affected. Each project install starts disabled. Use project-scoped secrets and issue short-lived invocation credentials where a plugin needs to call back into the host.

Matchmaking configurations can narrow a project's enabled features and grants. Resolve scope from verified tickets, room membership, or stored job metadata. Check current grants at every host boundary, including indirect calls from UI, jobs, scripts, and other plugins. Bind grants to the registered plugin and approved resource scopes. A permission change takes effect on active access. Promotion requires an explicit grant for new or expanded permissions. Rollback uses current grants.

### Enable, promote, drain, disable, and remove

1. **Enable.** Validate configuration, grants, dependencies, and readiness before activating the installed version. A match-scoped call requires enablement in both project and matchmaking scopes. The dashboard reports runtime health separately from enablement. If a dependency is unavailable, return a bounded failure for affected calls and preserve the saved configuration so it can recover.
2. **Promote or roll back.** The operator promotes an installed version per project after validating its config and migration compatibility. Atomically publish a new revision for new work. Existing rooms and assigned work keep their pinned plugin, rules, and settings versions. Cancel incompatible unmatched tickets with a requeue reason. Retain registered versions while referenced. When replacing a Go image, drain action rooms whose workers will restart and include older compatible versions needed by durable rooms. Roll back new work to a retained, schema-compatible version.
3. **Disable with dependencies.** Preview affected plugins and project or matchmaking scopes. Apply the operator's dependency cascade as one validated change. Block new calls, jobs, subscriptions, admissions, and assignments at affected scopes. Cancel queued and provisioning matches if their matchmaking capability is disabled. Stop optional features in existing rooms while keeping play available when required runtime capabilities remain enabled.
4. **Drain or stop gameplay.** Persist the scope transition and deadline. Default to a configurable five-minute drain. Only already active rooms can advance, reconnect existing players, and commit results during that window. At the deadline, pause turn-based rooms at the last committed state and interrupt live action rooms. The operator can resume a paused room once its pinned runtime and rules are available and permitted again. **Stop now** ends affected rooms immediately and preserves durable records. Use immediate stop for security revocation. Recheck the lifecycle revision at assignment and result commit to settle races with disable.
5. **Remove.** Uninstall from one project after its active work is resolved, revoke that project's grants, and preserve its durable plugin data. Remove a version from the server registry only when references in all projects are resolved. Treat data deletion as a separate operator action. Audit installation, grants, promotion, rollback, disable, drain, stop, and removal.

### Extension points and replacement

Expose named extension points for every feature, including auth providers, data and file backends, admin views, workflow steps, realtime events, and game runtimes. Multiple plugins can add contributions to an extension point. A replacement requires an explicit grant and operator selection, with one active replacement per named point and scope. Validate the replacement's contract before activating it and report failures to the operator. The host continues to enforce project isolation, identity, grants, quotas, and audit across replacements. Auth plugins provide identity evidence for their provider. The host verifies account links and issues sessions.

## Identity and sessions

Each user has a stable project-scoped ID and can link several sign-in identities. All five sign-in methods use the same project-scoped session model. Enable each method per project and choose open or invite-only registration. Operators can share one-time invite links or codes manually.

- **Username and password.** Enforce project-scoped unique usernames. Use Argon2id with unique salts and rate-limit password hashing and verification. Let users register independently of email delivery. When delivery is configured, support verified recovery email and expiring one-time reset tokens. Show recovery availability at signup and revoke existing sessions after a password reset. [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) [OWASP password recovery](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)
- **Mobile phone.** Use an SMS one-time code through a configurable provider. Normalize numbers to E.164 and set destination, resend, attempt, and spend limits. Treat phone sign-in as end-user access and protect phone-number changes with recent authentication and verification of the new number. [OWASP SMS authentication considerations](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html)
- **One-time login.** Interpret this as a code sent to the user's email address. For email and SMS challenges, bind the code to the project, destination, and purpose. Store a keyed digest, expire the code quickly, consume it atomically, and cap sends and guesses per destination, IP, and project. Return generic responses to reduce account enumeration. [OWASP email identity guidance](https://cheatsheetseries.owasp.org/cheatsheets/Email_Validation_and_Verification_Cheat_Sheet.html)
- **Guest.** Create a restricted account with its own project user ID so a player can join and retain progress. Apply tighter creation and gameplay quotas. Upgrade a guest by adding a verified sign-in method to the same account. If the identity already belongs to another account, report the conflict and preserve both accounts.
- **Google.** Use Google OpenID Connect and map the verified issuer and subject to the project user. Verify the signature, issuer, audience, expiry, and nonce and bind the callback to the initiating flow. Linking another sign-in method requires explicit proof of control and recent authentication. [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect)

Use a local-only test inbox to simulate email and SMS deliveries in the Compose test stack. Reject fake delivery configuration in production and keep codes out of ordinary logs. On the VPS, projects can enable username and password, guest accounts, and Google once its credentials are configured. Keep SMS, email codes, and email recovery disabled until real delivery is configured.

Use one hosted sign-in page across web and native clients. Browser sessions use `Secure`, `HttpOnly`, `SameSite` cookies, exact allowed origins, and CSRF protection. Sites on unrelated domains can put the backend behind a first-party proxy to keep cookie sessions first-party. Native clients can open the system browser and exchange an authorization code with PKCE for a short-lived opaque access token and rotating refresh token. Use platform-backed secure storage for refresh tokens where available and in-memory credentials on targets without it. Store session token digests server-side. Support logout, expiration, reuse detection, and explicit revocation. Guests can start through a direct API call. [OWASP session management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) [IETF native app authorization](https://www.rfc-editor.org/rfc/rfc8252)

## PostgreSQL tables and API exposure

- Give each project a PostgreSQL schema for its physical tables. Keep auth, exposure settings, files, jobs, and rooms in a protected platform schema. Use project-qualified keys, relationships, and row-level policies on tenant data in the platform schema. Give each project separate restricted API and direct SQL writer roles, plus a schema owner for migrations. Keep runtime roles out of ownership, schema creation, and `BYPASSRLS` privileges. Fully qualify database objects and use a fixed trusted search path for platform code. [PostgreSQL schemas and privileges](https://www.postgresql.org/docs/current/ddl-schemas.html)
- Define native columns, constraints, indexes, and same-project relationships in PostgreSQL. Publish selected ordinary tables as named API resources with a stable primary key and explicit column, operation, and filter allowlists. Start with supported scalar and JSON types, single-column primary keys, bounded cursor pagination, and parameterized filters. Build identifiers only from validated exposure metadata. Detect schema, grants, and trigger drift and suspend the affected resource until the operator validates and republishes it. Apply that workflow to both dashboard changes and external migrations.
- Default exposed operations to deny. Offer server-only, authenticated member, record owner, and explicit public-read policies. Apply row-level security under the project's restricted runtime role, bind caller identity transaction-locally, and deny access when required identity is missing. For owner policies, configure a typed owner column and derive its value on API inserts. Keep owner changes operator-controlled. Use a database-maintained version for optimistic edits so direct SQL updates also advance it. [PostgreSQL row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)
- Resolve project and caller for every operation. A public project ID selects configuration. Privileges come from operator sessions, end-user sessions, or scoped project server credentials. Store server credential digests and support expiry, rotation, and revocation. Apply the same resource checks to file access, subscriptions, function invocation, and room membership. Use idempotency keys for retried creates and function writes.

## File storage

- Keep object keys private and generated by the service. A file record tracks the project, owner, object key, content type, size, and upload state. Serve v1 uploads and downloads through the Go API for consistent authorization and hard request size limits in both deployment profiles. Use timeouts and concurrency limits for transfers.
- Reserve quota and create a pending file record before accepting bytes. Enforce size and type rules while streaming, then publish the record only after the object write succeeds. Expire incomplete uploads, reconcile orphaned objects, and retry cleanup of failed deletes. Return protected downloads as attachments by default. Serve inline public assets from a separate origin with restricted safe content types and a deliberate publish operation. [OWASP file upload guidance](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)

## Realtime for apps and sites

- Start with one WebSocket endpoint for app subscriptions and a separate gameplay endpoint with independent queues and limits. A client requests a short-lived, single-use connection ticket over authenticated HTTPS, then sends it in the first socket message within a short deadline. Bind tickets to the project, session, and intended endpoint. Validate browser origins against the project's exact allowlist and cap pending unauthenticated connections. [OWASP WebSocket security](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html)
- Authorize each subscription and publish only to its permitted scope, such as the caller's records or a project-readable table. Consume committed PostgreSQL change events and send small invalidation messages for affected scopes, including both old and new owner scopes when visibility changes. Clients subscribe before fetching, refresh when invalidated, and fetch again if an invalidation arrives during the fetch. On reconnect, resubscribe and fetch current state. Delivery is best effort and HTTP is the source of truth.
- Rate-limit messages, bound queues and frame sizes, and disconnect slow consumers so clients can resync. Handle session expiry and revocation on active sockets. Validate room and resource permissions when acting on a message and close or remove subscriptions when membership changes. Log connection and authorization failures with request or session references that cannot be used as credentials.

## Server-side functions

Use standard Go source in the dashboard from v1. Compile it to `wasip1/wasm` with a pinned toolchain. Use a versioned JSON contract for authenticated HTTPS calls, scheduled runs, and record-change events. Validate the toolchain and wazero runtime together on the supported host architectures. [Go WASI support](https://go.dev/blog/wasi) [wazero runtime configuration](https://pkg.go.dev/github.com/tetratelabs/wazero#RuntimeConfig)

1. **Edit and test.** The operator writes an entry point and helper packages in the browser. Resolve imports from the pinned project bundle and a reviewed set of Go standard library packages and platform SDK packages. Test drafts against JSON fixtures in the same runtime used in production. Show bounded diagnostics, test output, and proposed data changes. Test runs use fixtures and discard writes.
2. **Compile and publish.** Queue builds in a disposable, unprivileged compiler sandbox with a read-only toolchain, bounded scratch storage, and hard CPU, memory, and time limits. Disable network, automatic toolchain and module downloads, CGO, and user build commands. Build an immutable artifact pinned to its source, dependencies, toolchain, SDK ABI, and digest. After validation, switch the active version pointer atomically. Rollback selects a prior validated artifact. [Go toolchain selection](https://go.dev/doc/toolchain)
3. **Invoke and commit.** The API authorizes the caller and loads a bounded set of declared record inputs using the intersection of the caller's rights and the function's grants. Send bounded JSON on stdin and accept one validated JSON result and optional typed write intents on stdout, with capped diagnostics on stderr. Recheck permissions and input record versions, then commit valid intents with the idempotency key and result in one transaction.
4. **Isolate execution.** Run a fresh WebAssembly instance per invocation in an isolated worker. Provide the WASI services needed by the pinned Go runtime and bounded in-memory streams. Keep filesystem mounts, network, database credentials, and application secrets outside the script. Enforce linear-memory limits, process CPU and memory limits, and a wall deadline. Start with one concurrent compiler job, separate execution capacity for turns, and a one-second execution target subject to measurement. Keep compilation and execution outside the action-game loop. [wazero module and runtime configuration](https://pkg.go.dev/github.com/tetratelabs/wazero)

### Schedules and record-change triggers

- Use one PostgreSQL-backed job queue. Store schedules in UTC and enqueue a unique job for each due schedule and occurrence while advancing the schedule in the same transaction. After downtime, run the latest missed occurrence per schedule. The dashboard lets the operator pause a trigger, inspect sanitized status, and retry a failed run.
- Install platform-managed PostgreSQL row triggers on published tables. On insert, update, or delete, capture the event for realtime invalidation and enqueue any matching script jobs in the same transaction as the change. This covers writes through the API, interactive scripts, and ordinary direct SQL. Capture only bounded, approved fields and routing metadata. Reserve queue capacity per project and return a retryable error for the originating write if that capacity is exhausted. Limit routine writer grants to row operations. Pause exposure before DDL and revalidate the table and capture hooks before republishing. [PostgreSQL trigger behavior](https://www.postgresql.org/docs/current/sql-createtrigger.html)
- Give the capture hook only the privileges needed to validate the source and enqueue. Use a protected `SECURITY DEFINER` function with a fixed trusted search path, revoked public execution, and source validation against the registered table. Identify asynchronous script writes by their dedicated PostgreSQL login using `session_user`. Those writes still produce realtime events, and the capture hook suppresses recursive script triggers. [PostgreSQL security-definer functions](https://www.postgresql.org/docs/current/sql-createfunction.html#SQL-CREATEFUNCTION-SECURITY) [PostgreSQL session identity](https://www.postgresql.org/docs/current/functions-info.html#FUNCTIONS-INFO-SESSION)
- Pin the published script version on enqueue. Claim due jobs with short database leases, and execute as a project-scoped trigger principal. Before committing, verify the lease and that the trigger and its grants are still active. Commit validated writes and job completion together so a crash can repeat evaluation while the database effects commit once. Use bounded retry backoff and retain terminal failures for review. Process realtime invalidations independently of script runs. [PostgreSQL locking and queue claims](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE)

## Live multiplayer

Build a general room and matchmaking platform. The room plugin owns creation, admission, membership, reconnect, and result recording. Private invites and automatic matchmaking are separately enabled plugins. A game runtime plugin provides initialization, input validation, authorized views, and results through typed hooks. Each room pins its runtime, rules, and configuration versions. Tic-tac-toe and the co-op arena are example plugins using the same contracts as future games.

### Automatic matchmaking

- Give each project named, versioned matchmaking configurations with their own enabled plugins, game runtime, rules version, region, match size, eligibility settings, and ticket expiry. Queue tickets by project, config revision, and compatibility. The default matchmaking policy plugin selects eligible players in first-in, first-out order. Additional policy plugins receive a bounded candidate set and propose assignments. The host validates the group and owns admission and assignment state. Allow one active ticket per player per configuration and support cancel and status lookup.
- Create a provisioning room, reserve seats, and mark the selected tickets assigned in one PostgreSQL transaction. Recheck configuration and enablement before committing. Make enqueue retries idempotent and resolve a cancellation race by returning whichever state committed first. Send assignments privately over the gameplay control channel and allow HTTPS status lookup after reconnect. Joining a room requires a valid seat.
- Initialize the room outside the assignment transaction using the pinned rules version. Persist its provisioning status and initialization inputs so the service can safely retry after restart. Expire failed or abandoned reservations and allow players to queue again. When retiring a Go rules version, expire tickets and unstarted assignments for that version with an explicit reason that prompts clients to requeue. Active matches follow the action-room restart policy.

### Turn-based rooms

- Publish turn rules through the Go editor as versioned WebAssembly artifacts. Use two-player Tic-tac-toe to exercise publication, legal turns, wins and draws, idempotent moves, and reconnect. Give each ruleset room state, the verified player slot, the command, and explicit seed or time inputs. Require stable output ordering and verify repeated fixture runs for the pinned artifact. Recover from the committed state and player views. Run turns under a profile limited to pure computation and reserve capacity when background jobs are busy. [Go iteration semantics](https://go.dev/ref/spec#For_statements)
- Persist membership, turn, state, player views, and version in PostgreSQL. Authorize the player and check for a previously accepted command before evaluating a new one against the current committed state. Run the script outside database locks. In one transaction, recheck membership, room phase and version, validate the output, and commit the next state, views, and command ID together. Bind command IDs to the player and payload so a retry returns the original outcome and a reused ID with a different payload is rejected.
- Publish the new version after commit. A stale client reloads its authorized view. Keep the pinned bundle available for rooms that outlive a rule update or a service restart. A timeout or invalid rule response leaves the last committed room state available.

### Action rooms

- Target casual matches of 2–8 players in one region. The bundled Go worker runs a small co-op arena with movement, one shared objective, and a server-computed outcome. Private rooms support 2–8 players and the example matchmaking configuration starts with two-player groups. One worker room loop owns the match state in memory. Start at 20 Hz and send full snapshots at up to 10 Hz. Use bounded input queues and a capped catch-up budget. Keep database and script calls outside the simulation loop.
- Use private authenticated streams for inputs and snapshots in both bundled and separately deployed runtimes. The host assigns one runtime owner per room and validates membership, stream identity, and result commits. Bound queues on both ends and mark the room interrupted when ownership is lost. Use the bundled arena for the initial latency targets.
- Sequence inputs per player. Validate rates, membership, legal actions, and movement bounds. Coalesce continuous movement intent and deduplicate discrete actions. Snapshots include the server tick and the last resolved input sequence so clients can discard acknowledged inputs and interpolate between snapshots. Drop superseded snapshots from the outbound queue and disconnect clients that stay behind. WebSockets use TCP, so measure delay and head-of-line effects on degraded networks during playtests. [IETF WebSocket protocol](https://datatracker.ietf.org/doc/html/rfc6455)
- Allow a short reconnect grace period. A successful reconnect replaces the old socket and returns a fresh snapshot and input cursor. Persist a match record at start and commit the final outcome once by match ID before reporting completion. Retry transient result-write failures within a bounded finalization window. On restart, mark previously active action matches interrupted and surface that outcome to reconnecting clients.

## Client support

Keep the SDKs thin. Share the HTTP and socket contracts, example payloads, and protocol tests. Each client needs sign-in and sign-out, records, files, function calls, subscriptions, private rooms, matchmaking, gameplay, and reconnect. Keep retries limited to safe reads or operations with an explicit idempotency key. Use backoff with jitter after disconnects.

- **Browser JavaScript and TypeScript.** Provide a small client with browser cookie sessions, subscription resync, and room helpers. Include a sample site that signs in, updates a record, uploads a file, and invokes a function.
- **Flutter.** Provide one Dart package with native and web transport adapters. Flutter Web follows the browser session rules. Native Flutter uses the system-browser sign-in flow and secure refresh storage.
- **Native Android.** Provide a Kotlin client with coroutine-friendly calls and reconnect hooks. Protect refresh tokens with storage backed by Android Keystore keys. Test the app-link sign-in return and reconnect after backgrounding. [Android Keystore](https://developer.android.com/privacy-and-security/keystore)
- **Future Zarvan Engine SDK.** Develop the SDK in the Zarvan repository. The backend release provides a versioned HTTPS and WebSocket contract usable from Dart, with fixtures for authentication, matchmaking, room admission, player input, authorized snapshots, and reconnect. Use wire types an engine adapter can map into its own world state. [Zarvan architecture](https://github.com/arashrasoulzadeh/zarvan/blob/main/ARCHITECTURE.md)

## Analytics and Eye
