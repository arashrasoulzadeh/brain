Administrator guide

Operate every project as a separate boundary.

The host, not a plugin or client, owns project identity, permissions, lifecycle, worker supervision, and recovery decisions.

Plugin lifecycle

register → ready → install → grant → enable → promote
                                  ↓
                       drain → stop → recover
                                  ↓
                         remove / uninstall

Promotion rechecks readiness, configuration compatibility, requested grants, approvals, and pinned work. Removal and uninstall stop workers and close project-scoped sockets.

Before enabling

Confirm the version is registered, ready, installed for the intended project, and has only the capabilities declared by its manifest.

During incidents

Use drain for a controlled window, stop immediately for urgent isolation, and recover only through the host supervisor.

After changes

Check audit events, worker state, socket cleanup, project isolation, and the newest changelog entry for the pushed commit.

Security rules

  • Never authorize from client payloads, route parameters, object keys, or plugin-supplied project IDs.
  • Keep operator sessions separate from end-user sessions.
  • Keep runtime credentials unable to run DDL; use migration credentials only for schema changes.
  • Keep secrets out of logs, fixtures, screenshots, client bundles, and diagnostics.
  • Use parameterized SQL and validated identifiers.
  • Treat destructive operations as audited, reversible where possible, and protected by active-work checks.

Recovery command set

go test ./... and go vet ./... are local checks and do not start Docker. PostgreSQL/Compose commands are explicit release or integration checks and must document rollback evidence.
